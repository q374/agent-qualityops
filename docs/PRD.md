# Agent QualityOps 产品需求文档

> 版本：MVP 0.1｜日期：2026-09-18｜状态：独立轻量产品验证

## 1. 产品定义

Agent QualityOps 是面向 AI 产品经理、Prompt 工程师和应用研发者的智能体评测与质量运营工具。它把“凭感觉改 Prompt”变成可追溯的闭环：导入评测集、运行基线与候选版本、比较质量与成本、定位 Badcase、人工复核、执行发布门禁、导出证据报告。

本项目不宣称已在企业部署，也不替代 DeerFlow、Langfuse 或 Dify 的完整能力。它用于验证一条更聚焦的产品假设：小团队是否能用低成本、可解释的流程决定“一个智能体版本现在能不能发布”。DeerFlow 已有评测平台 RFC #4083 与相关实现，本项目是独立学习和产品验证，不重复声称首创或替代其平台。

## 2. 目标用户与问题

### 目标用户

- AI 产品经理：需要把业务要求转成可执行的质量门槛，并向团队解释发布决策。
- Prompt／Agent 研发者：需要比较版本、复现失败、定位回归，而不是只看平均分。
- 质量审核者：需要处理高风险与失败样本，保留人工判断和证据。

### 核心问题

1. 评测用例散落在表格和聊天记录中，缺少来源、风险和预期行为。
2. 两个版本的“更好”没有统一口径，质量、延迟、Token 与成本无法同时比较。
3. 平均分会掩盖高风险安全失败和严重回归。
4. 自动评分不确定，缺少人工复核、覆盖规则和审计记录。
5. 发布结论没有硬门槛，报告无法还原模型、Prompt、数据和人工判断。

## 3. 用户旅程

1. **准备用例**：导入带 `external_id`、来源、参考答案、关键词、风险等级和预期行为的 JSON 数据。
2. **配置版本**：创建基线与候选 Prompt 版本，记录模型和参数。
3. **发起评测**：选择用例与两个版本，设定运行模式和总预算；系统在超预算前停止。
4. **比较结果**：查看正确性、依据充分度、任务完成率、安全、延迟、Token 和成本。
5. **处理 Badcase**：按失败类型与严重度筛选，所有失败项和高风险项进入人工复核。
6. **作出决策**：系统按固定阈值生成允许发布或阻断发布，并列出阻断原因。
7. **导出证据**：导出包含版本、来源、时间、成本、自动评分和人工判断的报告。

## 4. MVP 功能

### P0 主链路

- JSON 评测集导入、字段校验、`external_id` 去重和来源展示。
- Prompt 版本新增与基线标记；密钥只从本地环境变量读取。
- 双版本批量运行；支持无外部调用的 `demo` 模式与显式选择的真实模型模式。
- 结果持久化：输出、三维评分、安全判断、延迟、Token、成本、失败分类和严重度。
- 版本比较、Badcase 列表、人工复核、发布门禁与报告导出。
- 审计时间线：记录数据导入、版本创建、运行完成、人工复核与门禁判断，支持按事件类型筛选。

### P1 后续迭代

- 评测集版本、变更记录、抽样策略和跨批次趋势。
- 可选且版本化的 LLM Judge；不得覆盖确定性安全失败。
- 模型、Prompt、Git 提交、工具集和关键配置摘要组成的环境指纹。
- 更细的角色权限、评论协作和 CI 门禁。

### 明确不做

- 不复制完整 LLMOps、Tracing、知识库或 Agent 编排平台。
- 不自动修改 Prompt、不自动发布线上版本。
- 不代替安全专家或法务审批，不对企业合规作保证。
- 不使用企业真实数据；首批 50 条均为公开资料衍生的合成测试。
- 不把自动分数当作业务效果或线上收益证明。

## 5. 数据与评分规则

- 初始数据共 50 条：20 操作咨询、10 故障排查、8 歧义输入、6 越界请求、6 提示注入／安全。
- 每条必须保留官方来源标题与 URL；“参考答案”是依据公开文档整理的验收预期，不代表官方原文。
- 确定性规则负责字段、关键词、安全拒绝和无效返回；LLM Judge 仅作可选补充；人工复核拥有最终覆盖权并保留原评分。
- 默认发布门禁：高风险安全失败为 0；依据充分度通过率不低于 90%；任务完成率不低于 80%；相对基线的严重回归不超过 3 条。
- 预算按整次请求统一控制，默认上限 5 元；达到预算立即停止，不自动追加。

## 6. 成功指标与验收

### 产品成功指标

- 50 条数据可一次导入，无重复 `external_id`，分类分布准确。
- 两个版本可完成同批用例运行并生成逐项差异。
- 100% 失败项与高风险项进入人工复核队列。
- 发布结论可解释：每个阻断项能回到具体用例、输出、规则和人工记录。
- 报告包含模型版本、Prompt 版本、用例来源、运行时间、成本和复核状态。

### 端到端验收

导入数据 → 创建两个版本 → 发起运行 → 查看比较 → 打开 Badcase → 提交人工复核 → 查看发布门禁 → 检查审计时间线 → 导出报告，全流程可在本地完成。模型超时、无效返回、评分失败和预算中断必须可见，不得伪装成成功。

## 7. 风险与约束

- **评分偏差**：自动评分仅作辅助，用固定规则、人工抽查与覆盖记录控制。
- **公开文档漂移**：保存来源 URL 与访问日期；变化时建立新数据版本，不静默改答案。
- **安全与费用**：密钥不入库、不回传；真实调用必须显式选择并受预算硬限制。
- **展示失真**：作品集和简历只写实际完成及验证结果；报名、提交、企业部署和开源采纳均需外部证据。
